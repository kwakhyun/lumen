# 서버 수집기 운영

운영 기준은 **매시간** 인증된 서버 수집기를 호출하는 것입니다. 스케줄 설정을 저장하는 것만으로 외부 호출기가 등록되지는 않습니다. 실제 연결 여부는 운영 화면의 최근 실행 기록에서 확인합니다. 아직 호출 기록이 없으면 `not_observed`로 표시하며, 정상 연결로 간주하지 않습니다.

외부에서 호출하는 Site MCP 도구는 `lumen_collect_due({"limit":1})`입니다. 서버가 이를 내부 함수 `tickDueSchedules({ ownerId, limit: 1 })`로 연결하며, `ownerId`는 요청 본문이 아니라 인증된 사용자에서 얻습니다. 호출자는 `ownerId`나 `siteId`를 지정할 수 없습니다. 인증된 계정의 모든 워크스페이스에서 수동 대기 작업과 예정된 수집이 대상이 됩니다. 먼저 `lumen_workspaces({})`로 워크스페이스와 예산을 확인하고, 결과는 `lumen_operations({"siteId":"소유한 UUID"})`로 읽습니다. `continuation: true`이면 `retryAfterSeconds`를 지키되 한 작업에서 수집 호출은 최대 10회로 제한합니다. 60초를 넘는 대기는 다음 예약 작업으로 넘깁니다. 별도 서비스 호출기는 전용 bearer secret이 설정된 `/api/operations/tick`을 사용할 수 있으며, 사용자 화면에 secret을 전달하지 않습니다.

수집기는 브라우저에서 시작한 대기 작업을 먼저 이어서 처리합니다. 예약된 작업은 사용자 시간대의 예정 시점 이후 첫 수집기 호출에서 실행하므로 매시간 호출 기준 최대 약 1시간의 지연이 생길 수 있습니다. 장기간 호출이 중단된 경우 누락된 모든 회차를 한 번에 청구하지 않고 회차 하나를 대기열에 넣은 뒤 다음 미래 일정을 계산합니다.

실행 기록이 한 번도 없으면 `not_observed`를 유지합니다. 실행 기록이 생긴 뒤 활성 일정이 있는데 **2시간** 넘게 수집기 기록이 없거나, 일정의 예정 시점이 2시간 넘게 지났으면 `attention` 상태로 표시합니다. 최근 수집기 실패나 열린 운영 알림도 확인 필요 상태입니다. 이 화면은 DB에 저장된 실제 실행 기록을 표시하며 외부 알림 전송의 성공을 의미하지 않습니다.

실행과 답변은 영속 lease로 중복 처리를 막습니다. 요청이 이미 제공자에게 전달됐을 가능성이 있는 답변은 중단 후 자동 재청구하지 않고 실패로 남깁니다. 실행을 다시 시작하면 새 사용량이 예약됩니다. 무료 예산은 수동과 예약 작업이 함께 사용하며, 한도 초과 회차는 `blocked`로 종료됩니다. 이전에 예약된 호출량을 실패 후 자동 환불하지 않습니다.

`tests/operations.test.mjs`는 실제 로컬 D1에서 동시 tick, tenant 격리, crash 복구, 예산 중복 차감 방지, 시간대/DST, 지연 및 실패 상태를 검증합니다. 테스트의 AI 응답은 fixture이며 외부 제공자 호출 비용이 발생하지 않습니다.


## 첫 예약 실행을 확인하는 순서

아래는 배포 후 시행할 절차이며, 이 문서를 작성한 시점의 프로덕션 실행 성공을 뜻하지 않습니다. 상세 운영 기준은 상위 [OPERATIONS.md](../OPERATIONS.md)의 “MCP contract and first unattended acceptance”를 따릅니다.

1. 배포된 Site의 MCP 도구 세 개가 실제 플러그인에 노출되고, 예약 작업과 워크스페이스가 같은 소유자로 인증되는지 확인합니다. 로컬 인증 헤더, 브라우저 쿠키나 서비스 우회 토큰을 예약 프롬프트에 넣지 않습니다.
2. 모든 소유 워크스페이스의 예정 일정과 수동 대기 작업을 살펴봅니다. `lumen_collect_due`는 특정 사이트만 고를 수 없습니다. MCP 운영 조회에는 수동 분석 작업 전체 목록이 없으므로 대시보드에서도 확인합니다. 완전히 빈 대기열일 때의 초기 호출은 외부 AI 요청 없이 heartbeat를 기록해야 합니다.
3. 실제 워크스페이스에 민감정보 없는 질문 하나를 직접 입력하고 연결된 모델 하나를 선택합니다. 다음 hourly 호출보다 앞서면서 현재보다는 미래인 시각으로 활성 일정을 저장합니다. `nextRunAt`, 일정 ID, 초기 무료 사용량을 기록합니다. 지난 시각을 고르면 다음 적용일로 넘어갑니다.
4. 제품 브라우저를 닫고 실제 클라우드 예약 작업이 MCP를 호출하도록 기다립니다. 수동 “지금 실행” 성공만으로 무인 실행을 검증했다고 하지 않습니다. 작업 로그의 실행 시각과 실제 도구 응답을 확인합니다.
5. MCP의 `isError:false`뿐 아니라 내용의 JSON과 영속 실행 결과를 봅니다. 질문 하나와 모델 하나라면 완료 1개, 실패 0개, live 원문과 provider 응답 ID, 해당 예정 시각 이후의 완료 시각을 확인합니다. 경쟁 작업이 없었던 경우 무료 예약량 증가가 정확히 1회여야 합니다. 인용이 0개인 정상 응답도 있으므로 출처를 만들어 채우지 않습니다.
6. 이어서 읽은 일정/실행 ID와 사용량으로 중복 생성이 없음을 확인합니다. 실패나 한도 차단은 성공으로 바꾸어 설명하지 않고 이력과 알림을 보관합니다. 시험용 일정을 계속 운영하지 않을 경우 일시 중지합니다.

`limit:1`은 처리 묶음 하나를 뜻하며 답변 하나를 뜻하지 않습니다. 묶음 하나는 대기 답변을 최대 두 개 처리합니다. 사용량은 처음에 질문 수 × 모델 수 전체를 예약하므로 중단 후 재개할 때 다시 차감하지 않습니다.

서비스 한도를 0으로 낮추면 **새 사용량 예약**을 막지만, 이미 예약된 실행과 이미 전송된 제공자 요청을 즉시 취소하지는 않습니다. 일정 일시 중지도 이미 시작된 작업의 취소 버튼이 아닙니다. 즉각적인 새 provider dispatch 차단이 필요하면 운영자가 해당 서버 제공자 연결을 비활성화하고 배포한 뒤 실제 연결 상태를 확인해야 합니다. 이미 전송된 요청은 완료될 수 있습니다.

## 호출 이력과 읽기 시점 관측

새 operation_ticks 이력은 서버에서 확인한 진입 경로와 호출 식별자, 시작/종료, 처리 건수, 제한된 오류 코드를 저장합니다. 원문이나 인증 정보는 저장하지 않습니다. 내 계정과 운영자 전용 서비스 범위를 구분하며 MCP 경로만으로 자동/수동 호출을 확정하지 않습니다. 최근 30일 최신 50개를 표시하고, 다음 호출 때 30일/범위별 1,000개/전체 10,000개 보존 한도를 적용합니다. 외부 수집기가 중지되면 물리 정리는 재개까지 지연될 수 있습니다. 이전 heartbeat를 전체 호출 이력으로 소급하지 않습니다.

운영 화면은 표시 중 60초마다 읽기 요청만 보냅니다. 오래된 heartbeat와 예정 시각 지연은 조회 시각을 기준으로 판단합니다. 새 AI 요청이나 즉시 실행은 만들지 않습니다. 실행 지연은 최신 50개 정기/직접 실행의 예정 시각에서 등록/종료 시각까지의 차이이며, 공급자 지연 또는 서비스 보장과 구분합니다. 종료 시각은 실패와 취소를 포함합니다. 자세한 계약과 지표 정의는 [개선 릴리스 기록](improvement-release-20261019.md)에 있습니다.
